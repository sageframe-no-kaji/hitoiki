# ho-01.1 — Fix pass for the spike

ho-01x run 1 returned ho-01 with five Must-fix findings. This ho answers them and nothing else. ho-01's spec and findings stay the record of what ho-01 did; the findings document is corrected in place because it is the artifact under review, and the one sentence in the spec that stated a wrong rule is corrected because ho-01 is not closed until its x ho passes. Everything else ho-01 recorded stands.

## Problem

From `ho-process/reviews/ho-01x-report-1.md`, each confirmed by the orchestrator against the code and the findings:

- **M1.** `PlainModel` emits a line only at LF and the harness flushes the line in progress only after the child exits, so under `--plain` a sudo prompt is invisible until the password has been typed. The findings claim at section 1 that the raw captures settle the prompt question; they do not. Run 10 saw no prompt because sudo's credentials were cached.
- **M2.** The findings and the spec's Decision 9 say status 255 is ssh's own and any other status is the remote command's. A remote command that exits 255 is indistinguishable from ssh's own failure.
- **M3.** Every reproduction block writes into `spike/captures/`, which is gitignored and never created; the harness opens the capture file without creating its parent.
- **M4.** The claim that every latency run opened a new connection rests on a grep for `ControlMaster` in the top-level config, which misses included files, `ControlPath` reuse, and the system config.
- **M5.** The claim that ssh read the key from disk under the scrubbed launch is inference; `IdentityAgent` could override the missing `SSH_AUTH_SOCK`.

Also taken in from the same review: Note N6, the capture count is 23, not 24; and from Codex's audit, the plain model's pending SGR buffer and an unfinished control sequence grow without bound, outside the line cap.

## Solution

**M1 — render the line in progress.** `PlainModel` gains a read-only view of the rendered line in progress (SGR bytes included, same rendering `takeLine` produces). The harness, in `--plain` mode, after every `feed`, writes to stdout the part of the line in progress it has not written yet; if the line no longer starts with what was written (a CR rewound it), it writes CR, the whole line, and `ESC [ K`, then continues from there. When the model emits a committed line, the harness writes only the unwritten remainder and LF, and resets its count. The ring still receives whole committed lines; nothing changes for the raw path. Bound the parser as well: an escape or control sequence longer than 256 bytes is abandoned (the bytes are dropped and the parser returns to ground); the pending SGR buffer is capped at 4,096 bytes, oldest sequences dropped. The run-sheet addition is one run, the practitioner's: run 10 again under `--plain` after `ssh host-a sudo -k`, with the rebuilt harness, typing the password at a prompt that is now visible. Its transcript and status line go into the findings under section 1 and section 6, and the section 1 claim is rewritten to rest on that run.

**M2 — state the rule the evidence supports.** The findings (section 3 Answer, and the For ho-02 list) and the spec's Decision 9 say: ssh exits 255 for its own failures, and a remote command's status passes through unchanged, so a remote command that itself exits 255 cannot be told from an ssh failure by the status alone; the text distinguishes the cases this spike recorded.

**M3 — create the directory.** Every reproduction block in the findings begins with `mkdir -p spike/captures`. The harness is not changed for this; the directory is a run-sheet prerequisite, and the sentence that says so goes at the top of the findings' reproduction notes.

**M4 and M5 — record the effective configuration.** The subagent runs `ssh -G host-a` (prints the effective client configuration; it opens no connection) and records, with placeholders, the lines for `controlmaster`, `controlpath`, `controlpersist`, `identityagent`, `identityfile`, and `identitiesonly`, plus `ls ~/.ssh` filtered for control sockets. The findings' latency conditions then cite that transcript for the fresh-connection claim, and the scrubbed-launch note says only what it shows: authentication succeeded under the scrubbed environment; the effective configuration names no `IdentityAgent` and one `IdentityFile`; how ssh authenticated is not traced.

**N6.** The findings' sequence table and prose count 23 captures; the build record's run-1 entry already carries the correction.

## Results

Closed 2026-10-25. All five Must-fix findings answered; ho-01x runs again as run 2.

- **M1.** `PlainModel` exposes the rendered line in progress; the harness writes it incrementally under `--plain`, rewriting from column zero with `ESC [ K` when a CR rewound it. Local demonstration: `prompt: ` on screen at 0.1 s, the newline at 2.1 s. The practitioner's run 11, `sudo true` under `--plain` after `ssh -tt host-a sudo -K`, showed the prompt before anything was typed, in a wrong-password run (status 1, 12.3 s) and a correct one (status 0, 2.2 s); the capture holds the prompt and ssh's closing line, 68 bytes, no typed byte. Parser bounds added: a sequence past 256 bytes is abandoned, pending SGR is capped at 4,096 bytes; the 256-byte bound covers OSC and DCS strings as well as CSI, recorded as a fact for ho-04.
- **M2.** The findings and the spec's Decision 9 now state the rule the evidence supports; the spec's correction is marked in place.
- **M3.** `mkdir -p spike/captures` opens every reproduction block; one sentence says why.
- **M4, M5.** `ssh -G host-a` recorded: `controlmaster false`, `controlpersist no`, no `controlpath`, no `identityagent`, one `identityfile`; no control socket under `~/.ssh`; the system and included config files set none of these. The fresh-connection claim cites that; the scrubbed-launch note says only that authentication succeeded and names the configuration.
- **N6.** 23 captures in ho-01; 25 with `smartctl-2.raw` and `sudo-plain.raw`.

**Surprise during execution.** Run 10 reran twice under `--plain` and never prompted. The cause is not sudo's cache: `smartctl` is permitted without a password for the user on host-a (`sudo -n -l`), so item 10 could never prompt, and ho-01's "credential cache" explanation was wrong; both documents now say so with the correction marked. Two more facts for ho-02 came with it: sudo's timestamp on host-a lasts 60 minutes and is keyed to the terminal device, so `ssh host-a sudo -k` without a terminal clears the wrong record, and a prompt is not guaranteed on any remote sudo.

**Not changed.** The README (the practitioner's own rewrite, uncommitted) and Codex's efficiency audit (`ho-process/reviews/ho-01-efficiency-audit.md`, uncommitted, input to ho-02 and ho-04 Think).
