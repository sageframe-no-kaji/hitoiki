# ho-05.1 — Settings and macros

The first ho of Phase 3. Everything that persists in user defaults, and the window that edits it. ho-03 left a placeholder settings window with one line about the hotkey; this ho replaces it with the real one. The replan checkpoint of 2026-11-08 split ho-05 at the storage boundary (ruling 6): this ho is the user-defaults half, ho-05.2 is the history-file half.

What the user gets. Settings… from the gear opens one window. On it: the shortcut, where commands start, which terminal Open in Terminal opens, the appearance, three switches (history, menu bar item, update check), a Refresh Environment button, and nine macro rows. Every change takes effect as it is made and survives relaunch. In the panel, Command-1 through Command-9 put a macro's command into the input; nothing runs until Return.

**Out of scope:** the history file, recall, the control on the bar, Clear (ho-05.2); the update checker (ho-06); the app icon and the bundle (ho-06); transcript storage; any persisted key not listed in Decision 1; any dependency in `Package.swift`; any change under `Sources/HitoikiCore/`.

**Resolves** the overview's "Recorder edge cases" decision, and two questions K2 §2.4 left open, each by an amendment note dated 2026-11-09 under §2.4: the appearance override joins the settings; the working-directory mode has two values, not three.

**Carried in.** From ho-03: `Panel.init(directory:)` takes the setting; a stored directory is validated; `Hotkey.combination` and `displayName` stop being constants; the terminal list of Decision 12; Refresh Environment with ho-02x's N2 test. From ho-04.6x: N3, Open in Terminal's "could not be found" message kept through hide and show. From the replan: the comment on `inputSize` (ruling 4); the update toggle (ruling 5).

## Phase 1 — Think

Eight questions, settled with the practitioner on 2026-11-09 and 2026-11-10, one at a time.

### Decision 1 — The store: one `Settings` type, ten keys, absent means default

One type, `Settings`, in `Sources/Hitoiki/Settings.swift`, reads and writes a `UserDefaults` handed to it at init: `UserDefaults.standard` in the app, a throwaway suite in tests (`UserDefaults(suiteName:)`, removed at teardown), so a test never touches the practitioner's preferences. Every read goes to the defaults and every write goes to the defaults; the type holds no mirror of any value, so there is one copy of each setting in the process. An absent key reads as the default, in every case; a fresh install writes nothing until the user changes something.

The keys, each matched to the setting K2 §2.4 (as amended) names. These ten and no other; ho-05.1x lists them against this table.

| Key | Type | Default when absent | K2 setting |
|---|---|---|---|
| `shortcutKeyCode` | integer (Carbon virtual key code) | Space (`kVK_Space`) | shortcut |
| `shortcutModifiers` | integer (Carbon modifier mask) | Control + Command | shortcut |
| `directoryMode` | string: `home` or `fixed` | `home` | working-directory mode |
| `directoryPath` | string, a path | none | working-directory mode (the fixed path) |
| `terminal` | string, a bundle identifier | `com.apple.Terminal` | terminal for Open in Terminal |
| `appearance` | string: `system`, `light`, `dark` | `system` | appearance (§2.4 amendment, 2026-11-09) |
| `historyEnabled` | bool | false | history on/off |
| `menuBarEnabled` | bool | false | menu bar item on/off |
| `updateCheckEnabled` | bool | true | automatic update check on/off (§2.4 amendment, 2026-11-08) |
| `macros` | array of nine dictionaries `{name, command}`, both strings | nine empty slots | macros (K2 §4) |

`Settings` is `@Observable` (macOS 14), so the SwiftUI form binds to it directly and the three live effects (Decision 6) follow a change without a second channel. `@AppStorage` is not used: it would be a second reader of the same keys with its own defaults, which is the duplication ho-05.1x looks for.

### Decision 2 — Appearance: system, light or dark, one assignment

A three-way picker. The stored value maps to an `NSAppearance`: `aqua` for light, `darkAqua` for dark, nil for system. `NSApp.appearance` is set to it at launch and whenever the value changes. Every colour token already carries a light and a dark value (Theme), so the one assignment flips the panel, the settings window and the menu bar item together. This is pālana's ho-15 pattern, copied in shape, not in code.

### Decision 3 — Where commands start: home or a fixed folder, read at Return, validated at Return

Two modes. Home, the default, is the user's home directory. Fixed is a folder the user picks with the standard folder chooser from the settings window; the picker shows "Home" and "Other…", and once a folder is chosen it shows that folder's path as the selected entry. "Last used" is gone: every command runs in its own shell and nothing typed moves the app's directory, so a last-used folder could only ever equal one of the other two (K2 §2.4 amendment, 2026-11-09).

Panel reads the directory from `Settings` when Return is pressed, not at init, so a change applies to the next command. `Panel.init(directory:)` becomes `Panel.init(settings:)`; the tests' fixture hands in a settings instance over a throwaway suite with the test's directory as the fixed path, which is what `directory:` did.

Validation, at Return: if the mode is fixed and the path is not an existing directory, the command runs from home and the strip says so for that command, in the alarm colour, from Running through Done: the path, "could not be found", and that the command ran in home. The next command checks again. Open in Terminal uses the directory the last command actually ran in. (ho-03 recorded the silent 127 of a missing directory as `missingDirectory`; that test's behaviour is replaced by this one.)

### Decision 4 — The shortcut recorder: capture, four refusals, register-then-release

**What the user sees.** A row showing the current combination as symbols and a key name, `⌃⌘Space`. Click it: it reads "Type a shortcut" and takes the keyboard. Press a combination: it takes, the row shows it, and the panel answers to it from that moment. Escape cancels, the old one stays. A refused combination shows one line under the row, in the alarm colour, saying why; the old shortcut stays registered and working.

**The refusal set**, in the order checked, each with its message:

1. **No key.** Modifiers alone, or modifiers released with no key pressed. "Press a key with Command, Control or Option."
2. **No qualifying modifier.** Command, Control or Option must be held; Shift alone does not qualify. The exception is a function key, F1 through F19, which may stand alone, as macOS's own shortcut settings allow. Same message as 1.
3. **Taken by macOS.** Asked of the system, not kept as a list: Carbon's `CopySymbolicHotKeys` returns every system shortcut with its key code, modifiers and whether it is enabled. A candidate that matches an enabled entry is refused: "Taken by macOS." A candidate that matches a disabled entry is allowed. So Command-Space is refused where Spotlight owns it and allowed where the user has turned Spotlight's shortcut off.
4. **Refused by the system.** Decided by trying. The new combination is registered first, while the old one is still live. If `RegisterEventHotKey` returns anything but `noErr`, the message names the status as `Hotkey.statusText` does today ("… is unavailable (-9878). Another app or macOS may own it …") and nothing changes. Only after the new registration succeeds is the old one released.

Nothing else is refused, including combinations an app binds locally, which the system cannot see, and the current default, which goes through the same four checks.

**Invariant.** At every instant exactly one hotkey is registered: the old one until the new one has succeeded, then the new one. `Hotkey` gains a `replace(keyCode:modifiers:)` that registers the new reference, releases the old on success, and returns the status; the two registrations carry different `EventHotKeyID.id` values while both exist.

**Where the logic lives.** The four checks are a function in `Sources/Hitoiki/Shortcut.swift`: a candidate (key code, modifiers) and the system's list in, a verdict out, no AppKit, so the tests feed it lists and read verdicts. The display name is in the same file: the modifier symbols in the order macOS shows them (⌃ ⌥ ⇧ ⌘) and the key's name, from `UCKeyTranslate` under the current keyboard layout for ordinary keys and from a small table for the keys that have names and no character (Space, Return, Tab, Escape, Delete, Forward Delete, Home, End, Page Up, Page Down, the arrows, F1–F19). That table is the one list in the file and its comment says why it exists. The notice texts in `Hotkey.statusText` and the "is registered" line in settings use the display name of whatever is registered, not a constant.

**The capture.** Raw events, not characters: key code and modifier flags from `NSEvent`, translated to Carbon modifiers. The capturing view is a small `NSView` that becomes first responder on click, shows "Type a shortcut", and handles `keyDown` and `flagsChanged`; it is wrapped for the form with `NSViewRepresentable` and lives in `SettingsView.swift` with the form.

**Discovery, settled by the builder in the guest:** whether `CopySymbolicHotKeys` reports Command-Tab and the other app-switcher combinations. If it does not, a named list of the combinations the window server owns outright (Command-Tab, Command-Shift-Tab) joins check 3, with a comment naming this Discovery; if it does, no such list exists. The builder records which in its report and the Reflect records it here.

### Decision 5 — The terminal picker: six names, Other…, detected each time, missing stays in alarm

A pop-up listing Terminal.app first, then every terminal from ho-03 Decision 12's list that is installed, by its app name, then "Other…". The list of bundle identifiers, in `Sources/Hitoiki/Terminals.swift`: `com.apple.Terminal`, `com.mitchellh.ghostty`, `com.googlecode.iterm2`, `net.kovidgoyal.kitty`, `com.github.wez.wezterm`, `org.alacritty`. Detection is `NSWorkspace.shared.urlForApplication(withBundleIdentifier:)` per identifier, run every time the pop-up is built; the call is a Launch Services lookup and costs nothing worth caching, so there is no scan button and no cache.

"Other…" opens the standard file chooser limited to applications. The chosen app's bundle identifier goes into the same `terminal` key; the pop-up then shows it by name as the selected entry. Whether an app opens a folder when handed one is the user's to know.

Open in Terminal hands the directory to the stored identifier with the same call ho-03 built. If the identifier does not resolve, the strip says "<app name or identifier> could not be found." in the alarm colour, and the message stays through hide and show, until the next submission or a clear: the reason moves from `apply(failure:)`'s one-time parameter into stored state alongside `failedStart`, which is ho-04.6x's N3. In the pop-up a stored identifier that does not resolve shows as its identifier with "(not installed)" until another is picked.

### Decision 6 — The settings window: one page, SwiftUI in AppKit, one instance, live

One `NSWindow`, titled "Hitoiki Settings", holding an `NSHostingView` of one SwiftUI `Form`; the one place K2 §5 lets SwiftUI in. One page, no tabs: the settings in order (shortcut, where commands start, terminal, appearance, the three switches, Refresh Environment), then a Macros section of nine rows, each a name field and a command field. About 520 points wide. `SettingsWindow.swift` keeps its name and becomes the hosting window; `SettingsView.swift` is new and holds the form and the recorder's view.

Lifecycle: `HitoikiApp.showSettings` makes the window once and reuses it; the app activates so the window can take typing (an accessory app otherwise cannot); the close button hides it; the next Settings… brings the same window back where it was. The window is reached from the gear and from the menu bar item (Decision 7). Clicking it is a click-out from the panel, as today: the panel hides and keeps, and the hotkey brings it back.

Every change takes effect as it is made; there is no Apply and no OK. Three changes have a live effect outside the store and `HitoikiApp` owns all three: the shortcut (Decision 4, through `Hotkey.replace`), the menu bar item (Decision 7), and the appearance (Decision 2). The directory, the terminal and the macros are read from `Settings` at the moment they are used, so they need no effect. The history and update switches have no effect in this ho (Decision 9).

Theme: the window uses the system form look and the tokens only where the form has none (the alarm line under the recorder).

### Decision 7 — The menu bar item: a three-item menu, the icon's glyph as a template image

With `menuBarEnabled` on, an `NSStatusItem` of square length appears at once; off, it is removed at once; at launch it is made if the key reads on. Its image is a template image of the app icon's two ink shapes, the breath and the chevron, with no ground, so the menu bar tints it for light and dark itself. The source is the practitioner's `design/hitoiki-icon.svg` (gitignored, on his machine); the builder derives the glyph from it, the two paths cropped to their bounds on a transparent ground, and commits it as `Sources/Hitoiki/Resources/MenuBarIcon.svg` (or `.pdf` if the SVG does not load as a template image; `NSImage` reads SVG on macOS 11 and later), declared in `Package.swift` with `resources: [.copy("Resources")]` on the app target and loaded through `Bundle.module`. A resource declaration is not a dependency. The full app icon is ho-06's.

The menu, three items: **Show Hitoiki**, with the current shortcut shown as its key equivalent the way menus show keys; **Settings…**; **Quit**. Show Hitoiki calls `Panel.show()`. Settings… and Quit are the gear's two actions. Check for Updates joins at ho-06, here and on the gear.

`MenuBarItem.swift`, new, holds the item, the menu and the make/remove; it is measured by the floor (an `NSStatusItem` can be made in the guest without a screen of the practitioner's).

### Decision 8 — Macros: nine slots, Command-1 to Command-9 replace the input, never while Running

Nine rows in settings, each a name and a command, empty by default; the name is a label for the user and appears nowhere but settings. In the panel, Command-N puts slot N's command into the input, replacing whatever was there, with the cursor at the end, and runs nothing; an empty slot does nothing. Return then submits as any typed line does. The practitioner chose replace over insert at the cursor: a macro is a template to edit, and the field holds one line.

States: in Composing and in Done the load happens, since the input is there to type into. While Running the digits go nowhere: not to the input and not to the pseudoterminal, as every Command key but V is ignored today (Keystrokes). The route is `PanelWindow.performKeyEquivalent`, which already takes Command-key equivalents for the input; Command with a digit 1–9 reaches `Panel.loadMacro(_:)`, which reads `Settings` at that moment. Nothing about macros is cached outside the store.

### Decision 9 — History and update check: the switches only

Both switches are on the form and round-trip. `historyEnabled` has no effect in this ho; ho-05.2 reads it. `updateCheckEnabled` has no effect in this ho; ho-06 reads it. The update switch reads as on when its key is absent (replan ruling 5), which Decision 1's rule gives for free. Beneath the update switch, one line of text says what the check does: one request to GitHub for the latest release, once a day, nothing sent but the app's name and version. The README's Privacy section is ho-06's; this line is the disclosure K2 §6 asks for in settings.

### Decision 10 — Refresh Environment: the button calls Run, failure reaches the notice

A button on the form. It calls `Run.refreshEnvironment()`, which already waits for a running command's Done and never captures alongside a command. On success nothing is shown. On failure the panel's notice gets the same line a failed launch capture gets ("Login environment not captured (…); using the app's own environment."), through `Panel.note`. Panel exposes `refreshEnvironment()` for the form to call so the Run stays private to Panel.

ho-02x's N2 (run 2) lands here as a test in `Tests/HitoikiCoreTests/RunTests.swift`: the capture shell is a script that writes a marker file when it runs; a command that sleeps is started; refresh is called while it runs; the test asserts the marker is absent while the command is alive and present after its Done. No change under `Sources/HitoikiCore/`.

### Decision 11 — Carried small items

- `PanelWindow.inputSize`: the comment names the 18 as a deliberate departure from the pālana scale's top of 15, one line that is the whole interface when the panel appears, judged in the live app, and cites replan ruling 4 (`ho-process/hos/replan-after-ho-04x.md`). The value does not change.
- `Hotkey.displayName` becomes a function of the registered combination; `Hotkey.combination` is gone; the default lives in `Settings`.
- `Panel.terminal` (the constant `com.apple.Terminal`) is gone; the default lives in `Settings`.

### Decision 12 — One builder, the ho document as spec, one file joins the floor's exclusions

One Opus builder. No agent-task files: the three parts all touch `Panel.swift`, `PanelWindow.swift` and `App.swift`, so a second builder would collide, and the previous hos ran this way.

`SettingsView.swift` holds the SwiftUI form and the recorder's capturing view, neither of which can be driven without a window on a screen; it joins `App.swift`, `PanelWindow.swift`, `TranscriptView.swift` and `SettingsWindow.swift` in `scripts/coverage-floor.sh`'s exclusion, with its reason in the comment. Everything else new is measured: `Settings.swift`, `Shortcut.swift`, `Terminals.swift`, `MenuBarItem.swift`.

### Decision 13 — Escape closes the settings window

Escape in the settings window hides it, as the close button does. The same window comes back at the next Settings….

### Decision 14 — The app's own default shortcut is exempt from the system-list check

The system's list reports Control-Command-Space as an enabled macOS shortcut (the Character Viewer) on a Mac whose System Settings shows no such item, so the recorder refused the app's own default once the practitioner had moved off it. K2 §2.1 chose that default knowing the collision. The default, `Settings.defaultShortcut`, passes check 3 whatever the list says; checks 1, 2 and 4 still apply to it, so a Mac where macOS really holds it still refuses it at registration. The verdict function takes the exemption as a rule, with a comment naming this decision; a test feeds a list that holds the default enabled and expects it allowed, and a different enabled entry refused.

### Decision 15 — The terminal list is read when the pop-up opens

The list was built when the settings window was drawn, so a terminal installed while the window stood open was not offered until relaunch. It is read every time the pop-up is about to open, and when the window is shown. Still no cache and no button.

### Decision 16 — A macro is a command, no name

The name box is dropped (K2 §2.4 and §4 amended 2026-11-10). Each row is `⌘N` and one command box, monospaced, with a visible placeholder and the form's field look, so an empty row shows where to type. `macros` is stored as an array of nine strings; `Macro` as a type goes with the name. A stored array of dictionaries from the first build reads as nine empty slots.

### Decision 17 — Refresh Environment is dropped

The button and its row leave the window; `Panel.refreshEnvironment()` and its test go with them (K2 §2.2 amended 2026-11-10). `Run.refreshEnvironment()` stays, since launch uses it, and the N2 test of Decision 10 stays with it. The README's line that relaunching re-reads the shell environment is ho-06's.

### Decision 18 — The gear opens settings; Quit is in settings and on Command-Q

The gear's menu goes. A click on the gear opens the settings window directly. Settings gains a Quit button at its foot, which terminates the app through the delegate as the menu item did, so a running command is still killed first. Command-Q on the panel does the same, through `PanelWindow.performKeyEquivalent`, since an accessory app has no menu to route it. The menu bar item's menu is unchanged. ho-06 puts Check for Updates beside Quit in settings. Supersedes ho-03 Decision 13's menu; K2 §2.1 amended 2026-11-10.

**Tests for these.** Escape on the settings window hides it (in `SettingsTests.oneWindow` or beside it). The default-shortcut exemption, in `ShortcutTests`. Macros as strings, in `SettingsTests`, with the old dictionary shape reading as empty. The gear's action is `showSettings` and there is no gear menu, in `PanelTests`. Quit and Command-Q terminate the process, so they are witnessed live only; the test asserts the key equivalent reaches the terminate selector without sending it. The terminal list's re-read is in the form and witnessed live only.

## Phase 2 — Execute

### Vocabulary

- **The store**: the `Settings` instance; one per app, one per test.
- **Live effect**: a change that does something outside the store at the moment it is made: the shortcut, the menu bar item, the appearance.
- **Read at use**: a setting Panel reads when it needs it: the directory at Return, the terminal at Open in Terminal, a macro at Command-N.
- **The strip**: the status line beneath the transcript, where a failed start, a missing folder and a missing terminal are said.
- **The notice**: the lines under the input where the hotkey's failure and the environment's failure are said.

### Invariants

1. Nothing of Hitoiki's is written anywhere but the ten keys of Decision 1 in the one defaults domain. No file, no plist of the app's own, no cache.
2. Every setting round-trips: a value written, read back from a fresh `Settings` over the same domain, is the value written; an absent key reads as its default.
3. A macro never runs. Command-N changes the input's text and nothing else; only Return submits.
4. At every instant exactly one hotkey is registered. A refused combination changes nothing; an accepted one is live before the old one is released.
5. The recorder refuses exactly the four cases of Decision 4 and nothing else.
6. A missing fixed folder never reaches `Run.start` as `cwd`; home does, and the strip says so.
7. A missing terminal's message survives hide and show, and leaves at the next submission or a clear.
8. The settings window is one instance for the app's life.
9. The menu bar item exists exactly when `menuBarEnabled` reads true.
10. Nothing new is cached: every read of a setting outside a live effect goes to the store.

### Tests

Both suites run in the guest through `scripts/vm-test.sh`. The builder writes them from the invariants, not from the implementation. Each invariant above has at least one test; the partitions below are the ones the orchestrator reads for.

**`Tests/HitoikiTests/SettingsTests.swift`** (new), over a throwaway suite removed at teardown:
- Each of the ten keys: write, read from a second `Settings` over the same suite, equal; absent reads the default. `updateCheckEnabled` absent reads true; `historyEnabled` and `menuBarEnabled` absent read false.
- Macros: nine slots always; a slot written survives; an unwritten slot reads empty.
- The suite's dictionary after the tests holds no key outside the ten (invariant 1).

**`Tests/HitoikiTests/ShortcutTests.swift`** (new), pure functions:
- Verdicts: modifiers alone; Shift with a letter; a bare letter; a bare digit; F5 alone (allowed); Control-Command-Space (allowed against an empty list); Command-Space against a list where it is enabled (refused) and where it is disabled (allowed); Command-Tab per the Discovery's outcome.
- Display names: `⌃⌘Space`, `⌥⇧F5`, a letter under the current layout, a named key from the table.

**`Tests/HitoikiTests/HotkeyTests.swift`** (existing, extended), real Carbon registrations in the guest:
- `replace` to a free combination: `noErr`; the old reference is released; a second `replace` back works.
- `replace` to the combination the process already holds under another id (or a combination registered by the test first): non-`noErr`; the first stays registered (a second registration of it from the test fails with `eventHotKeyExistsErr`, which proves it is still held).

**`Tests/HitoikiTests/TerminalsTests.swift`** (new):
- Detection over the list returns Terminal.app on any Mac and only identifiers that resolve.
- The display name of a resolved identifier is the app's name; of an unresolved one, the identifier marked not installed.

**`Tests/HitoikiTests/MenuBarItemTests.swift`** (new):
- Made with the setting on: an item exists, the menu has the three titles in order, the first item's key equivalent is the registered shortcut's. Setting off: the item is gone. Flipping on, off, on: one item at a time.

**`Tests/HitoikiTests/PanelTests.swift`** (existing, extended):
- Directory: with fixed mode and an existing folder, `pwd` prints it; change the setting between two commands, the second prints the new one (read at use). With fixed mode and a folder that does not exist, `pwd` prints home and the strip carries the path, "could not be found", and the alarm colour from Running through Done; the next command with the folder restored prints it. `missingDirectory` is replaced by this.
- Macros: Command-1 in Composing puts the command in the input, cursor at the end, state still nil, no child in the process table (invariant 3); with text already in the input, replaces it; an empty slot leaves the input as it was; in Done, loads; while Running, the input is unchanged and the command reads nothing (the pseudoterminal receives no bytes, by the pattern `escapeNeverWritten` uses); Return after a load runs the macro's command.
- Open in Terminal with a stored identifier that does not resolve: the strip carries "could not be found" in the alarm colour; hide, show, still there; a new submission clears it. (N3.)
- Refresh Environment through Panel: a failing capture shell puts the notice line on the panel.
- The hotkey notice and the settings line use the registered combination's display name, not a constant.

**`Tests/HitoikiCoreTests/RunTests.swift`** (existing, extended): the N2 test of Decision 10.

**Witnessed live only**, on the practitioner's run sheet: the recorder taking keys; the system list on a Mac with Spotlight on; each terminal opening a folder; the appearance flip; the menu bar icon's look; the settings window's placement.
