# ho-06.1 — The Build

The first ho of Phase 4. Hitoiki has run until now as a bare program built by SwiftPM. This ho makes it a real Mac app: a signed and notarised `Hitoiki.app` inside a disk image, built by one script on the practitioner's Mac. It also finishes the app's code. The update check is built, About and Check for Updates join the settings window and the menu bar item's menu, and settings gets a footer that stays in view. The ho ends with one full trial run of the pipeline. The practitioner installs the result on his own Mac, Gatekeeper opens it with no warning, he uses it, and he removes it.

What a user gets from this ho. They download a disk image, drag Hitoiki to Applications, and open it with no warning from macOS. When a newer version exists, a quiet line in the panel says so, and clicking it opens the project's site. Settings has About Hitoiki and Check for Updates at its foot, always visible. About shows the icon, the version, the maker's line with its links, and links to GitHub and to Buy Me a Coffee.

**Out of scope:** the code audit (ho-06.2); the technical document, the README, the screenshots, the GitHub repository, any push and the test release (ho-06.3); the site at `hitoiki.sageframe.net` and the Payhip listing (ho-07); any change to recall, history, macros or the panel's states beyond the update line; a migration of settings from the bare program; an uninstaller; two downloads; a styled disk image; any dependency in `Package.swift`; any change under `Sources/HitoikiCore/`.

**Resolves** the overview's deferred items for this ho: the update check's shape as built (Decisions 4 to 6), the icon (Decision 10), and the carried bundle items (Decision 13).

**Scope changed in the Think, by the practitioner's rulings of 2026-11-12.** ho-06 splits into three hos, and a ho-07 follows them (Decision 1). The README's word-for-word quote of the request and the test that proves it are dropped (Decision 4). The fresh-account test becomes a clean install on the practitioner's own Mac (Decision 14). The overview takes a dated note and K2 §6 takes an amendment note (see Changes).

**Carried in.** From ho-05.1's Reflect: settings now live under the bundle identifier, the resource bundle has to be placed where the app looks, and Check for Updates joins the foot of settings and the menu. From ho-05.1's second run sheet: About in the middle of the foot and in the menu bar item's menu, with a line about Sageframe. From ho-05.2's Reflect: `activate(ignoringOtherApps:)` in `showSettings` is witnessed again in the `.app`. From K2 §2.1: reopening the app from Applications brings the panel up, which only a bundled app can show.

### Decision 2 — Two builders, side by side, on separate files

The work splits cleanly by file, so two Opus builders run in parallel.

- **Builder A, the pipeline:** the build script, the entitlements file, the icon script, the icon files, the `.env` example and `RELEASING.md`. It touches no Swift file the app compiles.

### Decision 3 — Identity: `com.sageframe.hitoiki`, `Hitoiki`, 1.0.0, universal, no Dock icon

- **Bundle identifier: `com.sageframe.hitoiki`.** macOS keeps an app's settings under its identifier, so the `.app` finds none of the settings made in the bare program. The practitioner starts fresh. There is no migration code.
- **Name: `Hitoiki`,** in plain Latin letters, for the `.app`, Finder and the disk image's title. 一息 appears in About (Decision 8).
- **Version: `1.0.0`,** set in one place, the build script's `VERSION`, which the script writes into the Info.plist as both `CFBundleShortVersionString` and `CFBundleVersion`. The app reads its version from there, for About and the User-Agent. A program built straight from source has no Info.plist and so no version; it never sends the update request (palana's rule), so a developer's build never announces an update that does not exist.
- **Universal:** one app holding an Apple silicon copy and an Intel copy of the program, built per architecture and merged, as palana does. It is one download. The whole app stays under two megabytes. The Intel copy is built and signed but never run by us, since the practitioner's Mac and the test guest are both Apple silicon; `RELEASING.md` says so.
- **No Dock icon at all:** the Info.plist sets `LSUIElement` to true, so macOS never shows a Dock icon, not even for the moment before the code's `.accessory` call. The call stays, because the bare program has no Info.plist.

### Decision 4 — The update request: one GET, a memory-only session, no language header

The request, exactly:

- one `GET` to `https://api.github.com/repos/sageframe-no-kaji/hitoiki/releases/latest`
- no body, no query, no account, no identifier
- `User-Agent: Hitoiki/<version>`, set explicitly, where `<version>` is the Info.plist's short version
- `Accept: application/vnd.github+json`, the value GitHub recommends for its API
- no `Accept-Language` header, so the request carries nothing about the user's languages
- sent from a memory-only (ephemeral) session, so no cookie is kept and no reply is cached on disk

Whatever else Apple's networking library adds by itself (the host, compression, the connection) says nothing about the user.

The README does **not** quote the request word for word, and no test captures it from the wire. The practitioner's ruling: the code is open source, the README says plainly what the check does, and anyone can check that it is true; palana does the same. ho-06.3 writes the README's Privacy section in plain words: Hitoiki asks GitHub for the latest version number when it opens and once a day, sends only its name and version and nothing about the user or their commands, GitHub sees the internet address as with any website, and the check can be turned off in settings. Codex reads the code against this decision at ho-06.1x. K2 §6's amendment of 2026-11-08 takes a new dated note recording the relaxation.

### Decision 5 — When the check runs, and what counts as newer

- **Automatic checks** run at launch and then every 24 hours while the app runs, timed from launch. Each one reads the switch at that moment and does nothing when it is off. The last-checked time is held in memory only. No key joins user defaults.
- **The manual check** (Check for Updates) runs whatever the switch says. It does not move the automatic schedule. While it is in flight, the button reads "Checking…" and does nothing.
- **Newer** means: the release's tag, with a leading `v` removed, is one to three whole numbers separated by dots, and compared number by number (a missing number counts as 0) it is greater than the running version. A tag in any other form gives no notice. `v1.1` is newer than `1.0.0`; `v1.0` is not.
- **Failure** — no network, an error from GitHub, a reply that is not a release — is silent for an automatic check. For a manual check it gives the third answer of Decision 6.
- A build without a version (Decision 3) never sends the request, for either kind of check.

### Decision 15 — The language header is sent empty; a loopback test witnesses what is sent

Ruled 2026-11-12, during execution, on builder B's halt over Discovery 1. Apple's networking library adds `Accept-Language` by itself, filled from the user's language list (`en-US,en;q=0.9`; `fr-FR,fr;q=0.9` with French first), and no documented setting keeps it out. Setting the header to an empty value on the request sends `Accept-Language: ` with nothing in it. An undocumented session setting removes it completely, and a hand-written request on the lower-level network framework adds nothing; the practitioner chose the documented way. The request sets `Accept-Language` to the empty string, so it carries no language. Decision 4's "no `Accept-Language` header" and invariant 2's "no `Accept-Language`" read as "an empty `Accept-Language`". The library's own `Accept-Encoding` and `Connection` say nothing about the user and stand.

Because the library adds headers the built request does not show, one test sends a real check to a listener on the test machine's loopback address and reads the headers that arrive: `User-Agent` exactly `Hitoiki/` plus the version, `Accept-Language` present and empty, no body, no query. Nothing leaves the machine and GitHub is never reached. This test witnesses what is sent; it does not tie the README to a quote, which stays in plain words (Decision 4). If a later macOS fills the header in again, this test fails.

## Phase 2 — Execute

### Vocabulary

- **The check**: one sending of Decision 4's request and the reading of its reply. **Automatic** at launch and every 24 hours; **manual** from Check for Updates.
- **The running version**: the Info.plist's `CFBundleShortVersionString`; absent in a build from source.
- **The update line**: Decision 6's line in the panel.
- **The answer line**: Decision 6's line in the settings footer.
- **The footer**: Decision 7's pinned area at the foot of settings.
- **The app bundle**: `dist/Hitoiki.app`. **The disk image**: `dist/hitoiki-<version>.dmg`.

### Invariants

1. The check is the only network request in the app's code. No test sends a request off the machine.
2. Every check sends exactly Decision 4's request: `GET`, that URL, no body, no query, `User-Agent` exactly `Hitoiki/` plus the running version, `Accept` as given, no `Accept-Language`, from an ephemeral session.
3. An automatic check sends nothing when the switch is off at its moment; a manual check sends whatever the switch says; nothing is sent without a running version.
4. Automatic checks happen at launch and then every 24 hours, and at no other time. No key joins user defaults; the keys stay ho-05.1's ten.
5. The update line and the "is available" answer appear only for a tag that is newer by Decision 5's rule. An unparseable tag, an equal or older one, and every failure give no update line. An automatic failure shows nothing; a manual failure gives "Couldn't check for updates."
6. A manual check ends in exactly one of Decision 6's three answers, on the answer line.
7. Nothing about the check changes the panel's state, the input, the transcript, or a running command.
8. About Hitoiki and Check for Updates are reached from the footer and from the menu bar item's menu, whose items are in Decision 9's order. There is at most one About window.
9. The app bundle passes `codesign --verify --deep --strict`, runs with hardened runtime and empty entitlements, and holds exactly: `Contents/Info.plist`, `Contents/MacOS/Hitoiki`, `Contents/Resources/hitoiki.icns`, `Contents/Resources/Hitoiki_Hitoiki.bundle` and its contents, `Contents/_CodeSignature/CodeResources`, and, after stapling, `Contents/CodeResources`. The disk image holds the app bundle and the Applications shortcut, nothing else.
10. No committed file holds a signing identity, an Apple ID, a team number, a profile name or a password, other than as a placeholder.

### Tests

The Swift suites run in the guest through `scripts/vm-test.sh`. Builder B writes them from the invariants, not the implementation, and derives every expected value from an invariant or a decision. No test reaches GitHub: the fetch is handed to the checker, and the tests hand it a stand-in.

**`Tests/HitoikiTests/UpdateCheckTests.swift`** (new), no AppKit:
- The request (invariant 2): the request built for version `1.2.3` is a GET to the exact URL, with no body, no query, `User-Agent` `Hitoiki/1.2.3`, `Accept` as given, and no `Accept-Language`; the session's configuration keeps no cookies and has no cache. Discovery 1's answer is witnessed here in whatever form the builder found.
- Newer (invariant 5), each partition: `v1.1` and `1.1` over `1.0.0` are newer; `v1.0`, `v1.0.0` and `v0.9.9` are not; `v1.0.1` over `1.0.0` is newer; `v2` over `1.9.9` is newer; `v1.10.0` over `1.9.0` is newer (numbers, not text); `v1.0.0-beta`, `latest`, an empty tag and `v1.2.3.4` give no notice.
- The switch (invariant 3): an automatic check with the switch off calls the stand-in fetch zero times; on, once; a manual check with the switch off calls it once; with no running version, neither kind calls it.
- Answers (invariants 5, 6): a manual check gives "Hitoiki is up to date." for an equal tag, "Hitoiki 1.1 is available." for `v1.1`, and "Couldn't check for updates." for a failed fetch and for a reply without a tag; an automatic failure leaves no available version and no answer.
- The schedule (invariant 4): launch makes one automatic check; one tick of the daily timer makes one more; the timer's interval is 24 hours; a manual check in between does not add an automatic one. The test drives the tick directly; no test waits a day or sleeps in place of a moment.
- No new key in user defaults after any of the above.
