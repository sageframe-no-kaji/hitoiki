# ho-03.2 — Second fix pass for Panel

ho-03x run 2 returned ho-03 with one Must-fix finding, no Should-fix, and the two Notes of run 1 unchanged. This ho answers the finding and nothing else. The practitioner's ruling, 2026-11-02, reverses ho-03.1's: a submission in flight is undismissable, as a running command is; dismissal cancels nothing. ho-03.1's Results stay the record of what it did; its Results get a one-line note pointing here.

## Problem

From `ho-process/reviews/ho-03x-report-2.md`, confirmed by the orchestrator against the code:

- **M1.** ho-03.1 made dismissal cancel the submission task, with the task checking for cancellation after it awaits the login-environment capture. Two gaps remain in which `state` is still nil, so `canDismiss` is true and a dismissal hides the panel, after which the command runs hidden: between the cancellation check and `run.start` taking effect (an actor hop), and between `start` returning and Panel's state consumer applying `.running` (a second task). Codex reproduced the second with no change to the reviewed code: `submit("sleep 30")` after the capture, a yield and a 50 ms pause on the main actor, then a dismissal before Running was delivered, left a hidden panel and a live `sleep`. The System Design's lifecycle rule says nothing survives the panel; cancellation cannot close a gap that ends in another task.

Not taken: **N1** and **N2**, the same boundaries as run 1 (the cursor and Terminal tests cannot witness drawing and opening; the Panel tests' process-table reader and owned environment duplicate RunTests' across two test targets). Both stand as recorded in ho-03.1.

## Solution

**In flight is undismissable.** The submission handle ho-03.1 added, `submission: Task<Void, Never>?`, now marks the whole interval from Return to Running, and the one dismiss rule reads it:

- `submit` sets `submission` as now. The task no longer clears it on return and no longer checks for cancellation. It is cleared in exactly two places: in `enter(_:)` when `.running` arrives, and in `submit`'s catch branches when `start` throws (the failure is shown as now). After either, the panel is dismissable again.
- `canDismiss` is `true` unless `state` is `.running` or `submission` is non-nil. Still one computed property, read by every dismiss path; `dismissIfAllowed()` no longer cancels anything.
- `killForQuit()` first awaits an in-flight submission (`await submission?.value`), then kills and waits for Done as now. Quit therefore ends a command caught in flight the same way it ends a running one, without relying on the pseudoterminal's hang-up at process exit. The wait is bounded by the capture's five-second deadline.
- The one-submission-at-a-time guard stays. The doc comment on `submission` changes to say what it now means.

What this costs, recorded for the practitioner and for run 3: on the first command after launch, Escape, click-out and the hotkey do nothing for up to five seconds while the login environment is captured; the panel shows Composing with the typed line still in the input during that wait. After the first command `launch.value` returns at once and the interval is a few milliseconds.

**Tests**, in `PanelTests`:

1. *In flight is undismissable* (replaces `dismissalCancelsSubmission`): with the launch task held on the gate, `show()`, `submit("echo ready; read -r line")`, `await Task.yield()`, then `dismissIfAllowed()` and `toggle()`: the window stays visible and key, `canDismiss` is false, `state` is nil. Open the gate; Running at the readiness point; `canDismiss` is still false. Write a carriage return; Done; `canDismiss` is true and `dismissIfAllowed()` hides the panel.
2. *The reviewer's probe*: with the launch complete, `show()`, `submit("sleep 30")`, `await Task.yield()`, `usleep(50_000)`, `dismissIfAllowed()`: the window is still visible. Then `running()`, `stop()`, Done as `.signal(…)`, the group empty in the process table, and the panel dismissable.
3. *Quit in flight*: with the launch task held on the gate, `submit("sleep 30")`; start `killForQuit()` in a task; open the gate 100 ms later; `killForQuit()` returns with `state` `.done(.signal(9), …)` and the group empty.
4. `oneSubmission` stays as it is.
