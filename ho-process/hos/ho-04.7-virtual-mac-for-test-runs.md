# ho-04.7 — The virtual Mac for test runs

Runs the verification stack inside a macOS guest on this Mac, so the Panel suite's windows open where there is no screen of the practitioner's; nothing in the app changes.

---

## Problem

The Panel suite builds a real floating window and makes it key some sixty times a run. Every run takes the practitioner's screen and keyboard for its duration, and every verification needs one run: ho-04.6 cost four of them. Placing the test window off every screen needs a hook in production code, since the panel re-places itself on the mouse's screen at every show, and would still take the keyboard; ho-04.6's Reflect rejected it. The replan checkpoint of 2026-11-08 ruled the fix (ruling 1): run the tests where there is no screen of his, a macOS guest under Tart, and make a script in the repo the way tests run from here on.

Until this ho closes, the standing rule holds: one stack run per verification, asked for before it runs, the pointer parked on the screen the practitioner chooses.

---

## Solution

A macOS guest under Tart, on Apple's virtualisation framework, cloned from a published base image (not the image with Xcode inside), with the Command Line Tools and a Swift 6.4 toolchain installed inside it to match the host's. The guest has 6 GB of memory and four cores and runs only during a test run. A script, `scripts/vm-test.sh`, starts the guest headless, copies the working tree in over SSH without `.build`, runs the six verification commands inside, brings the log back with each command's exit status, and stops the guest. A note in `CLAUDE.md` makes the script the way tests run. Builders and the orchestrator call it from then on. Nothing under `Sources/` or `Tests/` changes; `Package.swift` gains nothing, since Tart is a tool on the host and not a dependency of the package.

### The host, as found

Apple silicon, 16 GB of memory, ten cores, 82 GB free on disk. macOS 27.0.1 (26A434). Xcode 27.1; `swift --version` reads `Apple Swift version 6.4 (swiftlang-6.4.0.34.1 clang-2100.3.34.1)`, target `arm64-apple-macosx27.0.0`. Homebrew 7.0.12. Tart not installed. `rsync` 3.4.1 from Homebrew; `expect` from the system. At `def1383` the stack gives 64 app tests and 71 core tests, 0 failures, coverage 95.76% on HitoikiCore and 93.73% on `Sources/Hitoiki`; the Transcript suite alone takes about 89 seconds.

### Decisions

**Decision 1 — The image:** `ghcr.io/cirruslabs/macos-golden-gate-base:latest`, the published base image for macOS 27, 38.4 GB on disk in the ASIF format, Homebrew inside. Ruled 2026-11-08 after the builder's first stop: ruling 1's 35 GB budget was set before the image's size was known, and the image alone exceeds it. The budget is now about 50 GB in all, with the builder's disk stop at a forecast past 55 GB; about 30 GB stays free on the host. The vanilla image (35.1 GB, no Homebrew) and the macOS 26 base image (about 30 GB, but compiling against the 26 SDK so the numbers may not match the host's) were declined. The image with Xcode inside (about 70 GB) stays declined by ruling 1. The pulled image stays under its published name in Tart's cache, generic, so palana, m4bmaker and ho-06's fresh-install test can clone it too; this project's clone is named `hitoiki-test`.

Tart itself is installed from the `openai/tools` Homebrew tap: the project moved from Cirrus Labs to OpenAI in 2026, the old `cirruslabs/cli` tap no longer installs under Homebrew 7, and Homebrew 7 asks for explicit trust of the tap's network helper (`softnet`) before it installs. Both steps belong in the provisioning record.

**Decision 2 — The toolchain ladder (Think, 2026-11-08):** three rungs, climbed in order, by command, inside the guest. (1) The Command Line Tools matching the guest's macOS, installed with `softwareupdate`. (2) If `swift test` there cannot find XCTest or Testing, or if the Command Line Tools' Swift is not 6.4, the swift.org Swift 6.4 toolchain package for macOS, about 2 GB, installed inside the guest and selected for the script's commands. (3) Xcode inside the guest is a stop point, never the builder's call: it needs the practitioner to clear disk first. The builder climbs rungs 1 and 2 without asking and stops before rung 3. The Results record which rung held.

**Decision 3 — Access (Think, 2026-11-08):** by key. At provisioning the builder puts the public key of the practitioner's SSH agent into the guest user's `authorized_keys`, entering Tart's published password once, by `expect` or by hand in the builder's own terminal, never in a committed file. From then on the script connects with `BatchMode=yes`, so it can never prompt. The committed script carries no password, no address, no key path and no host name: the guest is found by `tart ip` at each run, and the user is Tart's published default, `admin`, overridable by `HITOIKI_VM_USER`.

**Decision 4 — The guest's name:** from the environment variable `HITOIKI_VM`, default `hitoiki-test`. The script refuses to run, with a message naming this ho, if `tart list` does not show the guest.

**Decision 5 — What the copy leaves out:** `.build`, `.swiftpm` and `.git`, and `spike/captures`. The guest needs sources, tests, `Package.swift`, `Package.resolved`, the tool configs and `scripts/`; it needs no history and no host build products. `rsync --delete` so a second run reflects the tree as it is, including deletions.

**Decision 6 — The six commands, unchanged from `CLAUDE.md` plus the release build, run in this order:**

1. `swift-format lint --recursive --strict Sources Tests`
2. `swiftlint lint --strict`
3. `swift build`
4. `swift test`
5. `swift test --enable-code-coverage && scripts/coverage-floor.sh`
6. `swift build -c release`

Each runs in its own SSH session from the copied tree's root; the fifth is one session so its `&&` holds. Every command runs even when an earlier one fails; the script's own exit is 0 only when all six are 0. The rhythm runs `swift test` twice by design, so one run of the script carries the Transcript suite's 89 seconds twice; ruling 2's revisit trigger (a run passing three or four minutes) is measured against the numbers the Results record, not reopened here.

**Decision 7 — The log:** streamed to the terminal as it arrives and written to `.build/vm-test/<UTC timestamp>.log` on the host, inside the tree and already gitignored, with a summary at the end: each command, its exit status, its wall-clock seconds, and the total including boot, copy and stop. The script prints the log's absolute path last.

**Decision 8 — Lifecycle:** `tart run --no-graphics` in the background, wait for `tart ip` and then for SSH to answer (a bounded wait, two minutes, then a failure with a message), run, and `tart stop` on every exit path including interruption, through a trap. The guest is never left running by the script.

**Decision 9 — Provisioning is recorded, not scripted:** the commands that made the guest (install Tart, pull, clone, set memory and cores, push the key, install the tools) are written as a numbered record in this document's Results and as a comment block at the head of `scripts/vm-test.sh`, so the guest can be rebuilt from the record. They are not a second script: the guest is made once and cloned, and a provisioning script would be surface with no second user.

### Discoveries, each settled by a command in the guest

**Discovery 1 — The image.** Which published base image exists for macOS 27, and whether it boots under Tart on this host. Settled by `tart pull` and `tart run`, with `sw_vers` inside.

**Discovery 2 — The toolchain.** Whether the Command Line Tools alone give `swift test` what a package importing AppKit and swift-testing needs on macOS. Settled by `swift --version` and a first `swift build` and `swift test` on the copied tree, climbing Decision 2's ladder. If rung 2 also fails, stop: the practitioner rules between Xcode after a disk clear-out and anything else.

**Discovery 3 — The window server.** Whether a process started over SSH can create windows and make them key in the session of the guest's auto-logged-in user, which PanelTests needs. Settled by running the Panel suite over SSH. If a plain SSH session cannot, the builder tries, in order, running the test command through `launchctl asuser <uid>` for the console user, and a LaunchAgent in the console session that the script triggers and waits on; whichever holds is written into the script with a comment naming why. If none holds, stop and bring the options.

**Discovery 4 — The tools beside the toolchain.** Whether the base image carries Homebrew; `swiftlint` is installed with it, `swift-format` comes with the toolchain or with Homebrew, whichever the chosen rung provides. Settled by `which` inside the guest.

### What the builder does, and does not

The builder is one Opus subagent. It runs the setup commands on this host and inside the guest: installs Tart with Homebrew, pulls the image in the background under a Monitor (the download is long; no polling), clones the guest and sets its memory and cores, pushes the key, installs the tools, climbs the ladder, settles the three discoveries, writes `scripts/vm-test.sh` and the `CLAUDE.md` note, and runs the script until all six commands are green inside the guest. It runs the script, not the stack, so nothing opens on the practitioner's screen. It commits nothing. It runs the stack on the host only if the practitioner says so. It stops and reports at: no bootable image; rung 2 failing; the window server unreachable by every mechanism named; a disk forecast past 55 GB; and anything that would need the practitioner to type. (The first stop, 2026-11-08, was the disk forecast against the original 40 GB threshold; Decision 1 records the ruling.)

The orchestrator reads the script and the returned log, runs the script a second time from a clean shell to prove a second run is as good as the first, checks `tart list` and `df`, and commits.

## Results

Filled 2026-11-08 at close, from the builder's report and the orchestrator's own run.

**The image.** `ghcr.io/cirruslabs/macos-golden-gate-base:latest`, macOS 27.2 (26B123), 38 GB on disk in the ASIF format, Homebrew 7.0.12 inside. The pull took 9 m 19 s. Tart 2.41.1 from the `openai/tools` tap, with `brew trust --formula openai/tools/softnet` first (Decision 1 as amended).

**The ladder: rung 3 held, by a route the spec did not have.** Rung 1, the image's Command Line Tools 27.2 (Swift 6.4.2, Testing.framework, no XCTest; the tests import only Testing), compiled and ran the suite with the host's numbers once, then failed about half of all fresh test compiles with swift-testing's macro plugin (TestingMacros) missing from the build plan: 5 of 10 from-scratch compiles, not boot timing, not cured by `DEVELOPER_DIR` or by disabling explicit modules, and sticky once a plan was cached. Rung 2, the swift.org 6.4.2 toolchain, installs 5.08 GB, not about 2, and did not fit the guest's 6.6 GB free; it shares the build system and was declined. Rung 3 was ruled by the practitioner on new facts: this Mac's own Xcode 27.1 (27A9275) is 3.7 GB on disk because APFS stores it compressed (9.6 GB apparent), and was streamed into the guest with `ditto` keeping attributes, signature and compression, 3 m 20 s, 4.0 GB on disk in the guest; `codesign --verify` passes there. No download, no Apple ID, no disk clear-out. `swift --version` inside the guest now reads the host's exact string, `Apple Swift version 6.4 (swiftlang-6.4.0.34.1 clang-2100.3.34.1)`. After the copy: 10 of 10 from-scratch test compiles clean. The Command Line Tools stay in the image, unselected.

**The window server.** A plain SSH session reaches it. The image logs `admin` in at the console, the SSH session is the same user, and the Panel suite's `isKeyWindow` checks pass over SSH. Neither `launchctl asuser` nor a LaunchAgent was needed.

**Provisioning record.** Seven numbered steps at the head of `scripts/vm-test.sh`: Tart from the tap; the pull; the clone and `tart set --memory 6144 --cpu 4`; the key push, Tart's published password typed once; the Xcode copy and `xcode-select`, license, first launch; `brew install swiftlint swift-format` inside (0.65.1, 604.0.0); shutdown from inside.

**Runs.** The builder's two consecutive runs from a cleared guest `.build`: 326 s and 288 s, all six green. The orchestrator's run from a clean environment (`env -i`, PATH, HOME and the agent socket only): all six exit 0, total 288 s. Per command in that run: boot 9 s, copy 9 s, swift-format 9 s, swiftlint 6 s, `swift build` 20 s, `swift test` 114 s, coverage run and floor 114 s, release build 4 s, stop 3 s. Each test pass: 64 tests in 4 suites and 71 tests in 5 suites, all passed; HitoikiCore 95.76% over 5 files, `Sources/Hitoiki` 93.73% over 4 files, the host's figures at `def1383` exactly. The Transcript suite took 86.5 s in the guest against the host's 89 s. A whole run is 4.8 to 5.4 minutes, past ruling 2's three-to-four-minute trigger even though the suite itself is no slower; the trigger was written for the suite, and the practitioner rules on it at the next checkpoint, not here. Log of the orchestrator's run: `.build/vm-test/20261109T022305Z.log`.

**Disk.** Host free: 80 GiB at open, 33 GiB at close, 47 GiB spent against the amended 50 GB budget. `tart list`: `hitoiki-test`, 50 GB disk, 43 GB size, stopped; the base image 38 GB. Inside the guest about 2 GB stays free; a larger project or a second Xcode needs `tart set --disk-size` and a container resize inside.

**The screen and the keyboard.** Nothing appeared on the practitioner's screen in any run. He typed three rulings and no command: the ladder (Think 1), the key (Think 2), the image and budget after the first stop, and Xcode by copy after the second.

**What the spec did not anticipate.** `tart stop` cuts the guest's power; one build database came out corrupt, so the script shuts the guest down from inside first and `tart stop` follows on every path, 3 to 9 s. SwiftLint under the Command Line Tools needed `TOOLCHAIN_DIR`; under Xcode it needs nothing. The guest writes a `shutdown_stall` report at each shutdown; shutdowns still complete. `.keisaku.json` appeared untracked at the repository root during the session, written by the keisaku tool, not by this ho; left alone.
