# ho-04.6.1 — Fix pass for the Escape ladder

ho-04.6x run 1 returned ho-04.6 with three Must-fix findings, one Should-fix and two Notes. The orchestrator read each against the code on 2026-11-05 and the practitioner ruled on the one that touched a closed decision. This spec states what must hold, names the four places the code or the tests fall short of it, and prescribes no mechanism. Everything else ho-04.6 states still binds.

## Problem

From `ho-process/reviews/ho-04.6x-report-1.md`, confirmed by the orchestrator against `a5ee29a`:

- **M1, two things tangled.** First, `Run.signalGroup` refuses to signal once the leader is reaped, though Done has not been reported and members of the group may be alive; a clear in that window calls `kill()` and nothing is sent. That is a defect in Run. Second, a command that backgrounds a process and tells it to ignore the hang-up, the reviewer's `sh -c 'trap "" HUP INT; echo ready; sleep 30' & wait`, leaves that process alive after the leader exits and Done arrives; ho-04.6's invariant 3 said "no process of the cleared command's group is alive," which that survivor contradicts. ho-02 ruled on 2026-10-26 that after the leader exits, the kernel's hang-up on the closing pseudoterminal is what reaches the rest, "the same one a closing terminal window gives," and nothing is built for it. **Practitioner's ruling, 2026-11-05: ho-02's rule stands.** A process that detaches from the command by the means a terminal requires survives the panel as it survives a closed window; the invariant's sentence was the spec's overstatement, not a defect in the code.
- **M2.** `escapeClearsKilling` cannot tell whether the cleared command's Done was absorbed or applied and then overwritten, because it polls. The late-Done clause of invariant 3 has no conclusive test.
- **M3.** A start that fails before Running shows its reason on the strip; hide keeps it; the next show calls `apply()` without the failure and the strip empties and the output card hides. Invariant 2 says hiding loses nothing.
- **S1.** `hotkeyTakesKeyboard` decides whether to check the pending command from `isBusy` after the event, the value under test.
- **N1** (a start after a clear waits on the killed command's Done without a bound) and **N2** (the supersedes note's "Quit alone") stand as ho-04.6's Reflect recorded them; this pass changes neither.

## The invariant

ho-04.6's seven invariants hold, with invariant 3 restated and one sentence added to invariant 2. These supersede ho-04.6's wording; ho-04.6 is not edited.

**Invariant 2, hiding loses nothing**, now reads: after a hide and the show that follows, `state`, the transcript's text, the status, the offer, the input's text, and the reason shown for a start that failed are what they were before the hide.

**Invariant 3, a clear is total and final for the command it clears**, now reads: after a clear, the panel is Clean and visible with the keyboard in the input. If the command was alive at the clear, the signal the clear sends reaches its process group, whether or not the leader has already been reaped, and every process that signal reaches is gone. When the leader has exited and Run reports Done, the kernel's hang-up on the closing pseudoterminal reaches what remains of the group, as ho-02 ruled; a process that ignores it survives, as it would survive a closed terminal window, and nothing is built for it. Whatever Run reports about the cleared command afterwards — its Done, its last chunks — changes nothing on the panel, and that is observable: the panel exposes whether a cleared command's Done is still awaited, so a test can wait until it is not and then read the panel.

**Run's signal rule**, stated here because the fix is in Run: `interrupt()` and `kill()` signal the command's process group for as long as Run holds the command, that is, until Done is reported; the leader being reaped does not stop them. Run's public surface does not change.

## Solution

**M1, Run.** The guard in `signalGroup` reads whether a command is held, not whether its leader is unreaped. One test in the core suite: a command whose leader exits while a member of its group holds the pseudoterminal open and ignores the interrupt (`sh -c 'trap "" INT; sleep 30' & exit 0` is one such line) — the test waits until the process table shows the leader gone and the member alive, calls `kill()`, and asserts the group is empty and Done arrives. The core count grows by this one test.

**M1, the panel.** One test in the Panel suite that records the ruling: the reviewer's line, interrupted by Escape, reaches Done with the member alive; a second Escape clears; the panel is Clean and hidden by a third; the member is still alive, by the process table; the test then kills the group itself and asserts it empty. The test's description names ho-02's ruling and this one.

**M2.** Panel exposes, read-only, whether a cleared command's Done is still awaited; it is the fact Panel already holds for the waiting start, not a new one. `escapeClearsKilling` asserts it is true right after the clear that killed, waits until it is false, and then asserts the panel is Clean; the later assertions through the next command stay. A mutation that applies the cleared Done fails this test on every run, not on most.

**M3.** The reason for a failed start is a fact Panel holds until the next submission, the next Running or a clear, and `apply` derives the strip from it; nothing else writes the failure to the window. One test: a start that fails before Running, forced however the builder can (lowering the process limit for the duration of one start is one way; if no way exists without a hook, halt and say so), then hide and show, and the status, its alarm colour and the output card's visibility are what they were. The existing failure path's behaviour otherwise does not change.

**S1.** `hotkeyTakesKeyboard` decides from the rung whether the command must be shown untouched.
