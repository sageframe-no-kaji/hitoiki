# ho-06.2 — The Audit

The second ho of Phase 4. Every review so far read one ho's changes against that ho's spec. This ho reads the finished app as a whole before the final release build. Codex audits `Sources/`, `Tests/`, `scripts/` and `Package.swift` (about 12,400 lines, a little over half of them tests) for bugs, unclean code, code that can be tightened, chaff and AI-isms. Chaff is code, branches, state or comments that do nothing or answer no requirement. The practitioner rules on each finding. One Opus builder makes the ruled changes, and ho-06.2x reviews them in Codex.

The standard the audit serves, in the practitioner's words: careful, concise, clean, well-documented code that is direct and does not ramble.

**Out of scope:** any redesign (Decision 2); any dependency in `Package.swift`; the notarised release build, the technical document, the README, the repository made public and the test release (ho-06.3); the site and the Payhip listing (ho-07); any outward act; rewriting git history (the candidate profile names in `b21016c`'s text are ho-06.3's history sweep, and ho-06.1.1 ruled they stand).

**Carried in** from ho-06.1's Reflect, for the audit to rule on: `UpdateCheck.lastChecked` is held in memory and read by nothing but a test; `hdiutil create`, `attach` and `detach` print deprecation warnings on macOS 27.

**The spec is approved twice.** The Think below (Decisions 1 to 6) is approved before Codex runs. The practitioner's rulings on the findings are added under "Rulings" as Decisions 7 onward and approved before the builder starts.

## Phase 1 — Think

### Decision 1 — What an AI-ism is: the practitioner's list, plus an open door

Codex flags everything on this list as an AI-ism:

- Comments that narrate the code: a line saying what the next line does; doc comments on small private helpers that restate the name.
- Comments that tell the history of a change instead of the code's reason: "now returns X instead of Y", "fixed:", "previously…".
- Inflated or hedging words in comments and messages: "robust", "seamless", "comprehensive", "ensure", "gracefully", "Important:", "Note that", "should handle".
- Guards against cases that cannot happen: checks, fallbacks or default branches for states the code never reaches, with no requirement behind them.
- One-use scaffolding: a helper called once that only forwards; a constant named for its own value; a parameter or enum case nothing varies; a hook kept for later.
- Test padding: arrange/act/assert comments, test names that restate the assertion, helper layers that hide what a test does, assertions that copy a value from the implementation.
- Uniformity for its own sake: the same boilerplate repeated across files because one file had it.
- Rambling code: a function that does several things in sequence where each could be named; a file that has grown to hold more than one concern; long comments where one sentence says it; a roundabout path where a direct one does the same.

Documentation is kept, short, and says why. Anything else that reads to Codex as generated rather than authored goes in a separate section of the report, marked as outside this list.

### Decision 2 — What the audit may recommend: tighten and segment, never redesign

Fixed limits. No finding changes what one of K2's four components (Panel, Run, Transcript, Memory) is responsible for, or where its boundaries sit; adds a type, protocol or layer; or reopens a decision K2 closed. No new dependency. Behaviour is unchanged unless the finding is a bug; behaviour includes what the user sees and does, and what the app sends, writes and keeps.

Allowed: deleting code; folding a one-use helper into its caller; merging duplicated code or state; renaming; fixing comments; and segmenting. Segmenting means splitting a long function into named steps, or a file that holds more than one concern into files that each hold one, within one component. The practitioner wants code segmented appropriately, and Codex suggests it where it serves. A reorganisation of one file is one finding, not one finding per move.

If Codex judges that a closed K2 decision has turned out badly in the code, it says so as a Note naming the decision and recommends no change. Acting on it is a System Design question, not an audit finding.

### Decision 3 — Tests are held to the same standard, with one exception

`Tests/` is audited as `Sources/` is: bugs, chaff, rambling, AI-isms, a test that would still pass if the behaviour were wrong, a test that only repeats the implementation's assumptions. The exception: repeated setup that lets each test read on its own, top to bottom, is not a finding. Two guards: no finding deletes a test that is the only witness for a behaviour a spec asked for (it may rewrite it), and both coverage floors hold after the changes.

### Decision 4 — Process citations in comments: the reason in words first; a citation stays where it guards or illuminates

Every comment states its reason in its own words and makes sense to a reader who never opens `ho-process/`. A citation of a ho, a decision, an invariant or a System Design section stays in two cases: where the code makes a deliberate choice a reader would otherwise take for a mistake (the input at 18, the empty language header), and where it gives a reader real insight into how the Ho process shaped the code—a run-sheet ruling, a review finding that changed the code, a split. The practitioner is open about the process for this project and wants readers to be able to see it. A citation that stays comes after the reason and is written in full ("ho-06.1 Decision 15", never a bare "Decision 15"). Citations that only tag ordinary code are dropped. Codex reports this clean-up as one finding per file. (At the opening commit, 191 lines in 29 files cite the process.)

### Decision 5 — How findings reach the practitioner: two tiers, three grades

Every finding carries a tier and a grade.

- **Tier.** *Routine*: changes no behaviour and needs no judgment (a comment, a citation trim, dead code, a rename). *For ruling*: has real judgment in it (a bug, a segmentation, a change to how something works, a test rewrite, a Note on a K2 decision).
- **Grade.** *1*: a bug, or a breach of the seed's §8 or of a spec. *2*: debt the practitioner's standard names (Decisions 1 to 4) that a reader would feel. *3*: polish; the code is fine without it.

Codex merges findings that share one cause into one. The orchestrator reads every finding against the code before it reaches the practitioner; where he judges Codex wrong, the finding still goes, with his reason and a recommendation to leave it. Routine findings come as one list grouped by file, taken by default, with the practitioner striking what he keeps. Findings for ruling come one at a time, grade 1 first, in plain words with a recommendation. The practitioner may drop all grade-3 findings in one ruling.

### Decision 6 — Build-script changes are proven here by one local build

Ruled changes to `scripts/build_macos.sh` are made in this ho. If any ruled change touches that script, the orchestrator runs it once on the practitioner's Mac in local mode, with no signing identity and no notary profile (`CODESIGN_IDENTITY= NOTARIZE_KEYCHAIN_PROFILE= scripts/build_macos.sh --dmg`; a variable set in the environment, even empty, wins over `scripts/.env`), so nothing is signed with his identity and nothing reaches Apple. The run proves the app and the disk image still come out whole: the script exits 0, `codesign --verify --deep --strict` passes on the app, the bundle holds ho-06.1 invariant 9's list, and the disk image attaches and holds the app and the Applications link. The practitioner ruled that the orchestrator does this on his own, without asking. It is the one exception to "do not run `build_macos.sh`" in this ho. ho-06.1's notarised `dist/` is moved to `.build/dist-ho-06.1/` before the run and put back after it. The other scripts prove themselves: `vm-test.sh` and `coverage-floor.sh` run on every test run, and `make_icon.swift` is run once if a ruled change touches it.

## Phase 2 — Execute

### Step 1 — The audit

The orchestrator commits this spec and the Codex document `ho-process/audits/ho-06.2-audit-brief.md` together; that commit is the audit's commit. He runs Codex once, as a fresh `codex exec` session in the repository with the document's path as its prompt, never `resume`. Codex reads the code at that commit, runs `scripts/vm-test.sh` once for a baseline, writes `ho-process/audits/ho-06.2-audit.md`, and commits only that file. It changes nothing else.

### Step 2 — The rulings

The orchestrator reads the report against the code (Decision 5), then brings the findings to the practitioner: the routine list first, grouped by file, then the findings for ruling one at a time, grade 1 first. Each ruling is take, leave, or change. Rulings are written into this spec under "Rulings" and committed before the builder starts. A finding left stands in the record with its ruling.

### Step 3 — The changes

One Opus builder (`model: opus`) makes the ruled changes. Its instruction is this spec with its rulings, the report, the project `CLAUDE.md`, and the files the ruled findings name.

**Rules for the builder.** The rulings are the spec; the files the ruled findings name are the boundary, plus the test files a ruled change needs. Make each ruled change and nothing else; a change a ruling does not cover is a halt, not a judgment call. Behaviour is unchanged except where a ruling names a bug; each ruled bug gets a test that fails on the old code and passes on the new. No test that is the only witness for a spec'd behaviour is deleted. Tests run through `scripts/vm-test.sh` and nowhere else: never `swift test` or `swift build` on this host; call the script, wait for it, read the log it names. Never launch the app. Never run `scripts/build_macos.sh`. No commits. No new dependency. No force unwrap without a `// FORCE:` comment, no lint suppression without a reason. Halt and report if a ruling is ambiguous or cannot be made within Decision 2. Report: files changed, each ruling and how it was made, every command with its output, and the final green run with the log path, each command's exit, both test counts and both coverage numbers.

### Step 4 — Verification

The orchestrator reads the whole diff against the rulings, runs `scripts/vm-test.sh` himself, runs Decision 6's local build if `build_macos.sh` changed, sweeps for credentials, and commits with explicit paths. A diff that exceeds the rulings goes back with a re-brief. A run sheet follows only if a ruled change touches what the practitioner sees; the orchestrator asks before one, and checks `ps` for stale Hitoiki copies first.

### Step 5 — The review

At close, the orchestrator authors `ho-process/hos/ho-06.2x-review-of-the-audit.md` from `ho-process/x-ho-template.md`, over this ho's opening commit through its closing commit, with these ho-specific questions:

- Does every change in the range trace to a numbered ruling in this spec? Name any that does not.
- Is behaviour unchanged except where a ruling names a bug? For each ruled bug, which test fails on the old code?
- Was any test that is the only witness for a spec'd behaviour deleted?
- Was any finding ruled "leave" changed anyway?

The overview's ho-06x entry takes a dated note naming these questions for ho-06.2x. Codex runs up to three times, with fix passes between; a third Return stops.

### Invariants

1. The audit report is the only file Codex's audit run adds or changes.
2. Every change the builder makes traces to a numbered ruling.
3. Behaviour is unchanged except where a ruling names a bug, and each ruled bug has a test that fails on the old code.
4. No component's boundary moves (Decision 2); no type, protocol, layer or dependency is added.
5. Both coverage floors hold: ≥90% on HitoikiCore and on `Sources/Hitoiki`'s set, by `scripts/coverage-floor.sh`.
6. No committed file holds a signing identity, an Apple ID, a team number or a password other than as a placeholder; no host, address or user beyond Tart's default appears in a committed ho-process document.

### Done means

- `ho-process/audits/ho-06.2-audit.md` is committed, and every finding has the practitioner's ruling in this spec.
- The ruled changes are built and committed; the six commands are green through `scripts/vm-test.sh`; both floors hold.
- If `build_macos.sh` changed, Decision 6's local build passed.
- ho-06.2x passes in Codex.

### Verification

The orchestrator, after the builder returns:

1. `scripts/vm-test.sh`: all six commands exit 0, both "Test run with" lines in both test steps; the log read in full.
2. The whole diff read against the rulings; every test a ruling touched read against what it witnesses.
3. `git diff --stat a1b0a9b -- Package.swift` is empty; `git grep -n "URLSession\|URLRequest" Sources` finds only `UpdateCheck.swift`.
4. `shellcheck` on any changed script; Decision 6's local build if `build_macos.sh` changed.
5. Pre-commit on the staged paths; the sweep for credential-shaped strings across the tree, with the identity's and the team number's real values searched for by name; nothing committed names a host or a user beyond Tart's default.
