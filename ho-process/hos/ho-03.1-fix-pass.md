# ho-03.1 — Fix pass for Panel

ho-03x run 1 returned ho-03 with three Must-fix findings and three Should-fix. This ho answers all six, takes one of the three Notes, and nothing else. ho-03's spec stays the record of what ho-03 did; its Reflect gets a one-line note pointing here. The practitioner's rulings, 2026-11-02: dismissal cancels a pending submission; Run holds Done until its output has been taken, which opens `Sources/IssokuCore/` in this ho; the four comments are trimmed with no wider audit, the Must rating read as a Note; the font duplication is fixed now rather than left to ho-04.

## Problem

From `ho-process/reviews/ho-03x-report-1.md`, each confirmed by the orchestrator against the code:

- **M1.** `Panel.submit` awaits the login-environment capture inside a task before calling `start`. While it waits, `state` is nil and `canDismiss` is true, so Escape, click-out or the hotkey hide the panel; the task then starts the command with the window hidden. The System Design's lifecycle rule says nothing survives the panel; the seed says no command continues after dismissal.
- **M2.** Panel consumes `run.bytes` and `run.states` on two independent main-actor tasks. Run enqueues every chunk before it yields `.done`, but the states task can apply Done, and a dismissal can clear the transcript, before the bytes task has drawn the last chunks. Those chunks then appear in an empty hidden panel, or in the next command's transcript after `.running` cleared it. Decision 17 requires that every summons starts clean; Decision 10 requires that nothing is dropped.
- **M3.** Four doc comments summarise the method beneath them: `PanelWindow.layOut()`, `IssokuApp.main()`, `SettingsWindow.init(text:)`, `TranscriptPlaceholder.append(_:)`. ho-03's rule for the subagent: no comment that says what the next line does.
- **S1.** `launchTaskAwaited` asserts elapsed time from before the fixture was built, so it passes if the await is removed and window construction is slow.
- **S2.** `Fixture.trace()` samples `state` after `Task.yield()` and its two callers assert exactly three samples; a short command can pass through Running between samples. ho-03's Reflect named this as a watch item.
- **S3.** The transcript font and its line height are defined in `PanelWindow` (for `terminalSize` and the height cap) and again in `TranscriptPlaceholder` (for the text and the cursor), so the terminal size Run is told and the text it is drawn with can drift apart.

Also taken in from the same review: **N2**, the shortcut's display name written twice (`App.swift`'s registered line and `Hotkey.statusText`). Left: **N1** (the cursor test cannot witness drawing; the Terminal test does not call `openInTerminal`; both are the deliberate boundary of Decision 14 and the run sheet's evidence) and **N3** (the Panel tests' process-table reader and owned environment duplicate RunTests' across two test targets; kept, since the targets cannot share a file without a third target).

## Solution

**M1 — dismissal cancels the submission.** Panel keeps the handle of its one in-flight submission, `private var submission: Task<Void, Never>?`, set by `submit` and cleared when `.running` arrives or the task returns. `dismissIfAllowed()`, when it hides the panel, cancels it. After `await launch.value` the task checks `Task.isCancelled` and returns without calling `start`. Awaiting another task's value does not propagate cancellation to it, so the capture itself is unaffected. This is a task handle, not a second representation of the panel's state: `state` stays the one stored value, and ho-03x run 2 is told so. Tests: with a launch task that waits on a gate the test holds, `submit("touch \"$HOME/started\"; sleep 30")`, then `dismissIfAllowed()` hides the panel; the gate opens; after 500 ms `state` is still nil, the window is hidden, and `$HOME/started` does not exist in the fixture's owned home.

**M2 — Run yields Done only when its output has been taken.** Two changes in `Sources/IssokuCore/Run/Run.swift`, none to its public surface:

1. `Output.Iterator` reports a chunk as taken when the consumer comes back for the next one, not when the chunk is handed over: `next()` first reports the previous chunk's count, then awaits the next. A chunk the consumer is still holding is not yet taken. Backpressure moves by at most one chunk (16 KiB under a 1 MiB ceiling).
2. `finishIfDone` still records the exit and closes the terminal, but yields `.done` only when `untaken` is zero; otherwise the yield waits, and `taken` performs it when the count reaches zero. Until `.done` is yielded the ended child stays in place, so `start` throws `alreadyRunning` and `interrupt`, `kill` and the done waiters behave as they do today for a live child whose process has gone. `deinit` finishes both streams as before.

Together: Panel's bytes task has appended the last chunk and asked for the next before Run can publish Done, so Done, the clear at `.running`, and the clear at dismissal all follow the last draw. Panel does not change for M2. One known consequence: a consumer that never takes output never sees Done. Every consumer in the repository takes output; a Run test that awaits Done without draining must drain. The ho-02.1 regression that primes the queue to 256 bytes under the ceiling changes its first assertion: no command completes until consumption begins (before, the priming command did), and all 65 complete once it does. Tests: in RunTests, a command prints 64 KiB and exits; the consumer takes nothing for 300 ms, during which `.done` does not arrive, then takes everything and `.done(.status(0), …)` arrives. In PanelTests, the reviewer's probe: `submit("sleep 0.1; head -c 65536 /dev/zero | tr '\\000' x")` with the main actor held for 300 ms after `.running`; at Done the transcript holds exactly 65,536 `x`; `dismissIfAllowed()` then `show()`; the transcript is empty and still empty 300 ms later.

**M3 — four comments deleted.** The doc summaries on `layOut()`, `main()`, `SettingsWindow.init(text:)` and `append(_:)` go; every other comment stays. If SwiftLint then demands a documentation comment on any of the four, halt and report; do not write one back.

**S1 — the launch wait is witnessed.** `launchTaskAwaited` becomes: a launch task that waits on a gate the test holds; `submit("echo ready")`; after 300 ms `state` is still nil and no `.running` has been seen; the gate opens; `.running` then `.done(.status(0), retry: nil)` follow. The M1 test uses the same gate.

**S2 — `trace()` goes.** Its two callers give the command a readiness point and hold it: `submit("echo ready; exit 3")` waits for `ready` in the transcript while asserting `.running`, then awaits Done and asserts `.done(.status(3), retry: nil)`; the offer test's `-tt` leg waits for the fake ssh's `ok` the same way. No test asserts a count of samples.

**S3 — one definition of the transcript font.** `TranscriptPlaceholder` owns the font and its line height (internal, one place); `PanelWindow.terminalSize` and the height cap read them from there. `PanelWindow`'s `mono` and `lineHeight` are deleted.

**N2 — one display name.** `Hotkey` carries the combination's display name beside `combination`; the registered line in `App.swift` and `statusText` both read it. `HotkeyTests` keeps its independently written expected string.
