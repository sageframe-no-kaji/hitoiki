# ho-06.3 — The Documents

The third ho of Phase 4. It takes Hitoiki from a finished app on the practitioner's Mac to a public repository with a real release. A builder reads the code into a technical document and writes the README; the practitioner approves each and takes the README's three screenshots. The orchestrator sweeps the whole history, builds and notarises v1.0.0, and runs the clean install with the practitioner. Codex reviews all of that in ho-06.3x before anything leaves the Mac. Then, one yes at a time: the repository is created private, pushed, made public; the retry issue is filed; v1.0.0 is published as GitHub's Latest; a local 0.9.0 copy shows the update line against it.

**Out of scope:** any change under `Sources/`, `Tests/`, `Package.swift` or `scripts/` beyond Decision 9 (a scope change ruled 2026-11-14; any other defect found here goes on the record for a later ho); the site at `hitoiki.sageframe.net` and the Payhip listing (ho-07); rewriting git history without a ruling; any dependency.

**Changes to the overview, recorded here and as dated notes in `kamae-4-hitoiki-ho-overview.md` and `RELEASING.md`:**
- The README is written by a builder and approved by the practitioner, not written by him (session brief, 2026-11-14).
- ho-07 gates *selling*, not *releasing*: v1.0.0 is published on GitHub in this ho; Payhip waits for ho-07 (Decision 2).
- ho-06.3x runs before publication, not after the ho's last step (Decision 1).

### Decision 2 — One real release, nothing fake

Ruled 2026-11-14 (option A). v1.0.0, tag `v1.0.0`, is published as GitHub's normal Latest release, never a prerelease, and stays up. The tag points at the commit the release build was made from. ### Decision 3 — The technical document: `TECHNICAL.md`, in the root

Ruled 2026-11-14. One file at the repository root, linked from the README. Loose STE100 (Simplified Technical English): short sentences, one meaning per word, active voice, present tense. For a reader who never opens `ho-process/`. It covers, in this order:

1. How Hitoiki was made: with the Ho process, linked to the seed (`ho-process/kamae-1-hitoiki-seed.md`) and to https://hosystem.sageframe.net/. A short paragraph, not a history.
2. The four components—Panel, Run, Transcript, Memory—what each does and the files each owns.
3. One command's path from the shortcut to the exit status.
4. The update check, exactly what is sent and when.
5. About and Open at Login.
6. The build and release pipeline, pointing to `RELEASING.md`.
7. How the tests run: the guest machine (`scripts/vm-test.sh`) and the coverage floor.
8. Known limits, in plain words, not finding numbers: two update checks answered out of order can name the older of two new releases until the next check; a failed build leaves temporary folders the system clears; `hdiutil create` is deprecated and kept until it stops working; one unbroken line over 1 MiB streams slowly; the `-tt` retry runs the whole line again, an open issue.

Every claim is true of the code at the commit it is written against; the builder cites nothing it has not read.

### Decision 6 — The history sweep

The orchestrator's method; findings go to the practitioner. No scanner is installed and none is added. Over every commit's full patch (`git log -p --all`), and every path ever committed (`git log --all --name-only`), search for:

- credential shapes: private-key headers, `token`, `secret`, `password`, `api_key`, `gho_`/`ghp_`/`github_pat_`, `AKIA`, long base64 or hex runs, `Developer ID Application:` followed by a name, a ten-character team identifier;
- the redaction map's real names and addresses (State Memory), the practitioner's account name, home path and SSH key name;
- files that should never have been committed: `.env`, `*.p12`, `*.cer`, `*.mobileprovision`, `spike/captures/`, `dist/`, profiling data.

Known and ruled not secret: the notary profile candidates in `b21016c` (ho-06.1.1). Each other hit is listed with its commit and line for a ruling: stands, or rewrite history before the first push.

### Decision 9 — Three code changes go into v1.0.0

Ruled 2026-11-14 at the screenshot session, a scope change: this ho now changes code as well as documents, before the release build. One Opus builder; `scripts/vm-test.sh`; ho-06.3x reviews them with the rest. The panel screenshots are retaken after the change.

1. **The standard edit keys work in settings.** Hitoiki has no menu bar, so Command-V, C, X, A, Z and Shift-Command-Z found no Edit menu and did nothing in a settings text field; right-click Paste worked. The settings window sends each to the focused field as the panel already does for its own (`paste:`, `copy:`, `cut:`, `selectAll:`, `undo:`, `redo:`). A bug that every user setting up a macro meets.
2. **A macro field lets go of the keyboard.** Return in a macro field ends editing, and a click on the settings window's background ends it too. The value is kept, as on every change now.
3. **The command stays visible.** When a command starts, the input empties as now, and its placeholder shows the command in the placeholder's grey through Running and Done. Typing replaces it. Return on the empty input still runs only a `-tt` offer, so nothing runs again by accident. Escape that clears the result clears the placeholder; the next command replaces it; hiding and showing the panel keeps it, as it keeps everything else.

### Decision 11 — A hidden panel comes back to its starting place

Ruled 2026-11-14 at the retake. Dragged to the upper right, run, clicked out and summoned again, the panel came back at the bottom centre, about 80% below the screen, on a Mac with one display. The rule, as `PanelWindow.place()` already states it: a hidden panel shown again goes to its starting place, centred on the screen holding the mouse with its top a quarter of the way down, wholly on screen; a dragged position is not remembered. A builder looked for the cause: the code puts a hidden panel back at its starting place on every summons, and in the guest it always comes back there (a test that drags, runs, clicks out and summons, in eight variants, all passing on the unchanged code). A real drag goes through macOS's own window handling, which the guest cannot do; it seems to happen when the panel is pushed all the way up, and not every time. **Ruled the same day: no fix in this ho; filed as an issue once the repository is public**, with his yes. No code changed; the test was dropped. The issue's text:

> **Title:** The panel can come back mostly off screen after being dragged to the top
>
> Drag the panel all the way to the top of the screen (the upper right in the report), run a command, click outside, and summon it again: sometimes it comes back at the bottom centre, mostly below the screen. It should come back to its starting place, centred with its top a quarter of the way down. Not every time. macOS 27.0.1, one display, Stage Manager off. The code places a hidden panel at its starting place on every summons, and a test that sets the dragged frame in code cannot reproduce it, so the cause is likely in how macOS handles a real drag to the screen edge. Next step: a build that logs the panel's frame at each step.

## Phase 2 — Execute

### Steps

1. **Brief the builder** for `TECHNICAL.md` (Decision 3). Files it may touch: `TECHNICAL.md` only. It reads `Sources/`, `scripts/`, `Package.swift`, K2, this spec. Meanwhile the orchestrator builds the local copy and the practitioner takes the screenshots (run sheet below). Practitioner approves. Commit the README, the notes and `screenshots/`.

4. **The release build.** `ps` for stale Hitoiki copies; the settings plist and history folder removed so the install is first-run. `./scripts/build_macos.sh --dmg` at the commit to be tagged, each Apple upload with his yes; RELEASING.md's verification list run. 5. **ho-06.3x** authored from `ho-process/x-ho-template.md`, committed; Codex in a fresh `codex exec` session; up to three runs with fix passes between.
6. **Outward steps,** each stopping for his yes: `gh auth switch --user sageframe-no-kaji`; `gh repo create sageframe-no-kaji/hitoiki --private --description "Run one shell command from a floating panel."`; `git remote add origin git@github-no-kaji:sageframe-no-kaji/hitoiki.git`; `git push -u origin main` and `git push origin v1.0.0`; he looks; `gh repo edit --visibility public --accept-visibility-change-consequences`; `gh issue create` with Decision 13's title and body from ho-06.2; `gh release create v1.0.0 --verify-tag --latest --title "Hitoiki 1.0.0" --notes-file packaging/release-notes-1.0.0.md`.
