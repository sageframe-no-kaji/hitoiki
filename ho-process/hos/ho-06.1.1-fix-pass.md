# ho-06.1.1 — Fix pass for The Build

ho-06.1x run 1 returned ho-06.1 with three Must-fix findings, one Should-fix and one Note. The orchestrator read each against the code on 2026-11-13. One Must-fix is a defect in the code. The other two are lines the spec stated that the practitioner has ruled on, in this document; they change no code and no history. This spec states what must hold, names where the code and the tests fall short of it, and prescribes no mechanism. Everything ho-06.1 states still binds; where the two differ, this one does.

## Problem

From `ho-process/reviews/ho-06.1x-report-1.md`, confirmed by the orchestrator against `1918c06`:

- **M1.** A manual check that is still waiting for GitHub when the settings window closes sets its answer when the reply arrives, after `SettingsWindow.close()` has emptied it. The next time settings opens, it shows an answer to a question asked in an earlier opening. The same happens when settings is reopened before the old reply arrives. Decision 17 says the answer appears only after a manual check and is gone when the window closes. The tests always let the reply arrive before closing, so they pass with the defect.
- **M2.** Decision 3 says "The whole app stays under two megabytes." The notarised app is 2.5 MB; its universal program is 2.3 MB. Ruled below.
- **M3.** The spec's opening commit, `b21016c`, names the two candidate notary profile names; invariant 10 lists a profile name among what no committed file may hold. Ruled below.
- **S1.** `LoginItem.isOn` is stored beside `state`, and `read()` sets the two one after the other. Decision 20 asks for the switch to show what the service reports; the on/off is a function of the state, held twice.
- **N1.** Four comments: `App.swift:136` places the manual check's answer in the footer (superseded by Decision 17); `SettingsWindow.swift:5` calls settings the one place SwiftUI is allowed, though About is SwiftUI too (Decision 8); `LoginItem.swift:59` and `SettingsWindow.swift:135` restate their declarations.

## The practitioner's rulings, 2026-11-13

**On M2.** The app is 2.5 MB, the universal program 2.3 MB, the disk image 1.4 MB. Decision 3's size sentence was the orchestrator's estimate, given while the practitioner chose between one download and two; the ruling was one universal download, and it stands. There is no size limit. Nothing in the app or the pipeline changes.

**On M3.** A notary profile's name labels an item in the practitioner's keychain and authenticates nothing on its own; the name in question is already published in the public m4bmaker repository's `RELEASING.md`. Invariant 10 now reads: no committed file holds a signing identity, an Apple ID, a team number or a password, other than as a placeholder. A profile name is not counted among them. The history stands; nothing is rewritten.

## The invariants

ho-06.1's ten invariants and twenty-two decisions hold, with invariant 10 as ruled above and these changes.

**Decision 17, the answer's lifetime**, now reads: the answer line shows the answer of a manual check started since the settings window was last shown, and nothing else. An answer to a check started before the window last closed is never shown, whether its reply arrives while the window is closed or after it has been reopened. Partitions a test must cover, each with the reply held by the stand-in until the test releases it:

1. The check started, the reply released, the window open: the answer shows (as now).
2. The check started, the window closed, then the reply released: no answer, and none when the window is shown again.
3. The check started, the window closed and shown again, then the old reply released: no answer.
4. Partition 3, then a new check started and its reply released: that check's answer shows.
5. The answer shown, the window closed: the answer is gone (as now).

The update line in the panel is not tied to the window: a newer release found by any check, automatic or manual, still sets it (Decision 6), whenever its reply arrives.

**Decision 20, the switch's value**: the switch's on/off is derived from the service's last reported state, not stored beside it. The seven existing login-item tests still pass unchanged in what they expect.

## Solution

**M1.** The builder chooses how a check's answer is tied to the window's opening, and names the choice in the report. Tests in `UpdateCheckTests` or the settings-window suite for the five partitions, with a held reply, no sleep standing in for a moment.

**M2, M3.** This document records the rulings. No code changes.

**S1.** `isOn` becomes a function of the state.

**N1.** Each of the four comments says why, or goes; the two stale ones are corrected to what Decisions 8 and 17 say.
