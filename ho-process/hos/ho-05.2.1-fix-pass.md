# ho-05.2.1 — Fix pass for History

ho-05.2x run 1 returned ho-05.2 with two Must-fix findings and six Notes. The orchestrator read each against the code on 2026-11-11, and the practitioner ruled the failed Clear's message and which Notes to take. This spec states what must hold, names where the code and the tests fall short of it, and prescribes no mechanism. Everything ho-05.2 states still binds; where the two differ, this one does.

## Problem

From `ho-process/reviews/ho-05.2x-report-1.md`, confirmed by the orchestrator against `1aec109`:

- **M1.** `History.clear()` discards the error from deleting the file and empties the session either way. When the file cannot be deleted (a folder without write permission), Clear looks done, and the file's commands come straight back in recall. Decision 9 and invariant 7 say the file is gone and recall empty after Clear; the spec named no failure path, and the Reflect recorded the gap.
- **M2.** `Sources/Hitoiki/MenuBarItem.swift:29`: the orchestrator corrected one stale doc comment there ("settings' Quit", after Decision 11 removed that button) in the first-pass commit, and `MenuBarItem.swift` is not in ho-05.2's file table.
- **N1.** Entries are the trimmed text, so a command whose end is an escaped space (`cd My\ `) is recalled without the space, ending in a bare backslash.
- **N2.** No test turns the history switch on or off between commands, though Decision 1 states both transitions.
- **N5.** Three comments restate their declaration: `History.file`, `RecallList.rows`, `Panel.listOpen`.
- **N3, N4, N6** stand as recorded: N3's further list partitions, N4's nine-box discovery, N6's miscounted test line in ho-05.2. This pass changes none of them.

## The invariants

ho-05.2's twelve invariants hold, with these changes.

**Invariant 7, Clear**, now reads: after Clear, either the file does not exist and entries are empty until a command runs, or the file could not be deleted and the settings window says so. In the second case, a line in the alarm colour under the Clear History… button reads "History not cleared: <reason>". It stays until a later Clear succeeds or the settings window closes. Session memory is emptied in both cases. The file's commands remain in recall, as the line says. Clear deletes nothing else. Partitions a test must cover: a file deleted (entries empty, no line); no file at all (entries empty, no line: a file already gone is what Clear wants); a file that cannot be deleted (the reason reported, the file still there, session empty, entries the file's alone); a failed Clear followed by a successful one (the line goes).

**Invariant 5, entries**, now also reads: two commands are the same when they match with whitespace at their ends ignored, and an entry is the newest one's text exactly as it ran. A list choice and a taken suggestion load that text. `cd My\ ` comes back as `cd My\ `. Partitions: a command ending in an escaped space recalls whole; `df -h` run, then ` df -h ` in the file by hand, appears once, as its newest spelling.

**Decision 1's two transitions**, as tests only: history turned on after commands have run writes only later commands to the file, and the earlier ones stay in session memory; history turned off leaves an existing file byte for byte unchanged through later commands, and recall then shows the session alone.

## Solution

**M1.** `History.clear` reports a failed delete to its caller instead of discarding it; the settings form shows the line. How the failure travels is the builder's. The History partitions are tested in `HistoryTests`; the line under the button is tested in the settings-window suite if the form can be read there, and otherwise witnessed live and said so in the report.

**M2.** This spec's file table names the change, as ho-05.1's did for the same file. No code changes.

**N1.** Sameness stays trimmed; the entry and what loads is the text as it ran.

**N2.** Tests in `HistoryTests`, beside the on and off partitions.

**N5.** Each of the three comments says why, or goes.
