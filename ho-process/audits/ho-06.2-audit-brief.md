# ho-06.2 — The audit brief

You are auditing the whole finished Hitoiki codebase before its final release build. You did not write this code and you have no reason to defend it. This is not a review of one change: read every file in scope as it stands at this commit. Your output is one report. You change no other file.

**Goal**

A written report at `ho-process/audits/ho-06.2-audit.md` listing every finding in the format below, each with file and line, a kind, a tier, a grade and a proposed change, so the practitioner can rule on each one: take, leave, or change.

**Read, in this order**

1. The seed, §8 (Constraints) and §12 (What I Want to Learn): `ho-process/kamae-1-hitoiki-seed.md`.
2. The System Design, for the four components and the decisions it closed: `ho-process/kamae-2-hitoiki-system-design.md`.
3. The audit's spec, Phase 1, Decisions 1 to 6: `ho-process/hos/ho-06.2-the-audit.md`. These six decisions are your rubric and your limits. Read them closely; they are not repeated here.
4. `CLAUDE.md`.
5. The code in scope: every file under `Sources/`, `Tests/` and `scripts/`, and `Package.swift`. The earlier ho documents in `ho-process/hos/` are there when you need to know why a piece of code exists; read them for that, not as part of the scope.

**What you look for**

- **Bugs.** Code that does the wrong thing, or the right thing only by accident. Say how it fails: the input or sequence and what goes wrong.
- **Unclean code** and **code that can be tightened**: a direct path where the code takes a roundabout one; duplicated code or state; a long function or a file holding more than one concern that reads better segmented (Decision 2).
- **Chaff**: code, branches, state or comments that do nothing or answer no requirement. For each, say what requirement you looked for and did not find.
- **AI-isms**: the list in Decision 1, rambling code included. Anything else that reads to you as generated rather than authored goes in its own section, marked as outside the list.
- **Process citations** in comments, by Decision 4: one finding per file.
- **Tests**, by Decision 3.

Two items are already on record; give each a finding or say why it is none: `UpdateCheck.lastChecked` (`Sources/Hitoiki/UpdateCheck.swift`) is held in memory and read only by a test; `hdiutil create`, `attach` and `detach` in `scripts/build_macos.sh` print deprecation warnings on macOS 27.

**Limits** (Decision 2, restated as rules for you)

- Propose no redesign: no finding moves a component's boundary, adds a type, protocol or layer, or reopens a closed System Design decision. If you judge a closed decision has turned out badly, write a Note naming it and propose no change.
- Propose no dependency.
- A proposed change leaves behaviour unchanged unless the finding is a bug. Say so in each finding.
- Propose the change in one or two sentences: what changes, not the code for it.
- Merge findings that share one cause into one, listing every place.

**Running the code**

Run `scripts/vm-test.sh` once, for a baseline. It runs the build, the tests and the coverage floor in a Tart guest and saves a log under `.build/vm-test/`; it takes about six minutes. Wait for it. Do not run `swift test` or `swift build` on this host, do not launch the app, and do not run `scripts/build_macos.sh`. You may read and search anything.
